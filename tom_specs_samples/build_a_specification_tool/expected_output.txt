a literal is undiscoverable and rots silently when the model moves.

  it the class, kind and children a generic renderer needs.

3. The generated schema
==========================================================================
Each of the 14 document roots has a schema GENERATED from the model
and SHIPPED as data inside the facade package, under
`schemas/<document>/<document>.1.0.docspecs-schema.yaml`. A tool
loads one; it never writes one, and never derives one itself.

IT IS A DocSpecs SCHEMA, NOT JSON SCHEMA. It describes a *markdown*
document — headings, their ids, their formats, the form fields a
section carries and which of them are required. A tool reaching for
a JSON-Schema validator will not find one, because the artifact the
schema governs is not JSON.

  root section id : SBP
  section types   : 3915

  That count is large because a Solution Blueprint SEEDS the twelve
  Phase-3 documents: its own section classes ARE those documents'
  types, so its schema covers every section id they define. Step 5
  meets the same fact from the other side.

  A section type resolves by ID PREFIX, which is how a generated id
  like `DAENT-ENTI-7` finds its type without the schema listing
  every instance:
    DAENT-IDEN       -> DAENT_IDEN
    DAENT-ENTI-7     -> DAENT_ENTI_
    NOSUCH-1         -> (no type — a tool treats this as unknownSection)

4. Validation — three tiers, two of them here
==========================================================================
THIS IS THE DISTINCTION TOOLING AUTHORS MISS. A tool that wants one
tier and calls another gets nothing useful — not an error, just an
empty list that reads like a pass.

  STATIC tier   — checks the MODEL'S OWN ANNOTATIONS: field-type
                  rules, @ContentType compatibility, cycles, the
                  §10.2 structural invariants. Runs ONCE at
                  generation time, in
                  `tom_specs_clitool/lib/src/validator.dart`, and is
                  deliberately NOT part of the nine-language runtime
                  surface. Not reachable from this sample, and that
                  is the point: by the time a document exists, this
                  tier has already run.
  INSTANCE tier — checks A DOCUMENT'S VALUES against the model:
                  `validateDocument` (SOM §9). In every runtime.
  DOCUMENT tier — checks a MARKDOWN RENDITION against the generated
                  schema: `DocSpecsValidator` (SOM §14).

The two runtime tiers ask disjoint questions and neither implies the
other: `validateDocument` is not a completeness check (an absent
required field holds no value, so there is nothing invalid to
report), and the schema validator does not follow a reference it
sees filled. A tool that wants "is this document good?" runs BOTH.
