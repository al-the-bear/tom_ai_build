## Specifically for PQ-24

**How the extension handles an open ask today.**

1. **The turn waits inside the tool call.** `tomAi_askUser`, `tomAi_askUserPicker` and
   `tomAi_askInMdBrowser` are blocking tools. `llm_tools.md`, tool table: "Blocking … Waits
   **indefinitely** by default — the block *is* the pause, so a prompt running in the queue holds
   there until the user answers." The same holds for a tool approval and a plan proposal.

2. **The item stays `sending`.** It is not moved to another state; it gets the mark *waiting for
   your reply* (orange, with the time since when) and an ask panel
   (`multi_transport_prompt_queue_revised.md`, "An item waiting for the user"; user guide,
   "Waiting for your reply", "Answering in the item"; `vscimpb55`, `vscimpb173`).

3. **The run's lane sends nothing else.** A run has one lane and "one item sends per lane at a
   time … each run's items go in their order (a lane whose next item cannot start waits; its later
   items do not jump ahead)" (user guide, "One lane per run"; `vscimpb46`: "a blocked lane waits,
   never skips"). The waiting item occupies the lane, so no further item of that run is sent: not
   the next queue item, not the next todo of a walk (the walk is the same item), not its
   follow-ups. For the declared wait the guide says it in so many words: "Its run sends nothing
   else meanwhile; other runs do" (`tomAi_waitFor`; `vscimpb82`: "The item stays `sending` and its
   lane is held"). The run reports the state *waiting for user* (`vscimpb123`).

4. **The other runs go on.** The lanes send in parallel, and each run has its own ask slot: "asks
   of different runs are open at the same time … and answered in any order" (`llm_tools.md`,
   "One open ask per process run"; `vscimpb81`, DONE WHEN: "two sessions in different runs of one
   quest window can each have an open question (and a pending tool approval) at the same time").
   This is the reason `vscimpb81` was built: before it, one run's open question blocked every
   other run of the window.

5. **Nothing in the same run can ask a second time.** A second ask from the same run while the
   first is open is refused (same sources).

6. **The one thing of the same run that still goes out: a chat send in another session.** Chat
   sends are outside the lanes and hold one busy slot per session (`vscimpb46`: "Chat items stay
   outside the lanes"; `vscimpb135`). A chat send into the waiting item's own session is not
   started; the user chooses (as an update to the running prompt, next, after it, or in a free
   session). So the product owner's answer (b) describes today's behaviour for the queue exactly,
   with this one exception (VX-17).

7. **The ask does not hold the run's settings.** Auto-send stays on; when the ask is answered the
   turn goes on and the lane continues by itself. This differs from the *holds on a todo*: an item
   held at a `decision-needed` or blocked todo is not executing; it is put into the state
   `decision-needed` / `todo-blocked` and **its run's auto-send is switched off** (user guide,
   "A blocked todo holds the item", "An open decision holds the walk when it is next"). There, the
   user guide says "The held item does not hold the rest of the queue: restart the queue and the
   other prompts run"; an open *ask* has no such bypass short of skipping or stopping the item.

8. **Ways out for the user without answering** (`vscimpb55`, `vscimpb60e`): Continue offers
   *Resend this stage* and *Skip to the next todo / stage*, both of which close the ask
   unanswered; Stop puts the item back to staged; *Let the next item go first* takes effect only
   after the running iteration, so not while the ask is open. A soft interrupt counts a turn
   waiting in an ask as held at once (`vscimpb112`).

9. **The ask outlives a restart of the host** and is answered by a continuation prompt in the
   same session (`vscimpb166`, VX-3); the item stays `sending` through it, so the lane stays held
   across the restart.

**What this means for the text.** With (b):

- CP.21 becomes: "While an ask of a run is open, that run sends nothing further from its queue;
  the other runs go on." The clauses "the rest of the queue" and "a walk goes on with the next
  todo that does not depend on the waiting one" go: the extension never did the second, and a
  walk holds at the todo it cannot run (VX-27).
- CP.9 "the run resumes when the answer arrives" is right as worded; add how (VX-3).
- The lead-in of `RT-ASKS` ("it must not hold a process up for long") is then met by three things
  the extension has and the text should name: the other runs go on; the user can skip or resend
  the waiting item (VX-6); a held or waiting run is visible as such everywhere (VX-14, VX-15).
  The escalation chain (CP.18) is the fourth.
- Two points stay open and are put as questions above: whether a chat send in another session of
  the waiting run still goes out (VX-17), and whether "one open ask per run" stays a rule of its
  own (VX-1).
