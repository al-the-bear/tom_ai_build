==========================================================================
TomSpecs, end to end: a room-booking service for one office
==========================================================================

Six phases, six gates. `tom_specs_project_flow.md` is the authority
for all of them; this run executes them against real artifacts.

The project is deliberately small — two entities, one business rule,
one server operation — so that every artifact from idea to code fits
in one reading without losing the thread.

--------------------------------------------------------------------------

--------------------------------------------------------------------------
  artifact: spec/01_project_idea.md

PHASE 4 — CodeSpecs
--------------------------------------------------------------------------
  artifact: codespec/{shared,client,server}/

  IN   the accepted specification
  OUT  a skeletal application that COMPILES BUT DOES NOT EXECUTE,
       in three projects: shared, client, server.

  Phase 4 runs in two passes — a mechanical extract generator and a
  judgment-bearing authoring agent — and `phase4_codespecs_run`
  beside this sample walks that in full. This one runs the extract
  pass to produce the input, and then measures the OUTPUT PROPERTY
  the methodology stakes itself on.

  Extract pass: 27 areas, 3 populated (CE-API, CE-SU, CE-DB).

  SELF-SUFFICIENCY — the methodology's main promise to a reader.
  After Phase 4 the trio carries every fact its parts were routed
  from, so Phases 5 and 6 read CODE rather than reopening the
  Phase-3 documents (`codespecs_mapping.md` §9.6). It is not a
  claim anyone has to take on trust: two of the derivation
  contract's checks decide it mechanically, in both directions —

    check 35  every token the extracts hold a value for is cited by
              a back-link in the trio — an uncited token is a
              specification fact that reached no code
    check 36  every token a back-link names exists in the extracts —
              a trace to a token no area routed is stale or invented

  Both need the extracts, so both run only when `--extracts` is
  given. `tool/validate.sh` runs the validator twice for exactly
  that reason; its recorded output is below.

  $ validate_codespecs --shared codespec/shared --client codespec/client \
                        --server codespec/server

PHASE 5 — Test Derivation
--------------------------------------------------------------------------
  artifact: test/booking_rules_test.dart

  IN   the CodeSpecs code COMBINED WITH the Phase-3 specification.
       Neither alone is sufficient (PF-PHA-P5): the CodeSpecs supply
       the surface — what exists, with what types — and the
       specification supplies the semantics: what it must do, at
       what boundaries, with what errors.
  OUT  a test suite in which every test FAILS or SKIPS, because
       there is no implementation yet, plus a recorded baseline.

  FR-001 alone yields twelve tests in three groups. The split is
  the point: the rule, its boundaries, and its error paths —
  PF-PHA-P5 derives boundary tests and error paths as separate
  activities, not as an afterthought to the happy case.

    the rule        5 tests  overlapping, enclosing, enclosed, and
                             that it names WHICH booking clashed
    boundaries      5 tests  touching intervals do NOT conflict —
                             10:00–11:00 beside 11:00–12:00 is two
                             bookings, not a clash. Only the
                             specification says so; the CodeSpecs
                             surface cannot.
    error paths     2 tests  a zero-length or inverted candidate is
                             REJECTED, not reported conflict-free

  The baseline is a real recorded run, not a claim: the
  implementation was stripped back to the bodies Phase 4 emits
  (form 3a, `throw UnsupportedError(<the specification's own
  words>)`) and `dart test` was run. Result: +0 -12.

PHASE 6 — Implementation
--------------------------------------------------------------------------
  artifact: lib/booking_rules.dart

  IN   the CodeSpec elements, the derived tests, the dependency
       analysis
  OUT  code, written until the tests pass — and nothing more.

  WHAT PHASE 6 ACTUALLY WRITES IS SMALL, and that is the
  methodology's claim rather than an accident of this example. The
  Tom Framework owns authentication, authorization, transport,
  serialization, persistence and input handling; Phase 4 emitted the
  entities, the service unit and the wire shapes. What is left for a
  person to write here is a rule about intervals — which is why
  `lib/booking_rules.dart` has no framework dependency at all and
  runs under plain `dart test`.

  It is also why PF-GAT-G6 calls its security criterion tractable:
  the surface on which a security defect can be introduced is the
  business code, and the business code is this one file.

  THE TRACEABILITY CHAIN, which G6 checks as unbroken:
    requirement   FR-001  a booking must not overlap another
                          booking of the same room
    spec section  RSP FRE-REQU-…  ← SBP.9  ← the Project Idea
    CodeSpec      codespec/server/lib/src/services/booking_service.dart
    test          test/booking_rules_test.dart  (Phase 5)
    code          lib/booking_rules.dart        (Phase 6)

  $ dart test

What the walkthrough produced
==========================================================================

  phase  artifact                                    where
  1      Project Idea, free-form                     spec/
  2      Solution Blueprint, schema-bound            build/ (generated)
  3      IFM + RSP, at specification depth           build/ (generated)
  4      the shared/client/server trio + extracts    codespec/, build/
  5      12 derived tests + the RED baseline         test/, spec/
  6      the one business rule                       lib/

  Six gates ran. Every one of them can fail, and a failed gate
  returns the work to its phase — that rework loop is the normal
  case, not the exception (PF-FLW-OVE).

  Phases 7 (Application Candidate) and 8 (Release Candidate) are
  deployment, test-environment execution and business sign-off.
  They have no artifact a sample can carry and G7 requires a human
  signature by definition, so this walkthrough stops at G6 and says
  so rather than simulating them.

  THE POINT, in one line: every artifact above was DERIVED from the
  one before it, and each derivation was CHECKED before the next
  began. That is the whole difference between a methodology and a
  document template.
