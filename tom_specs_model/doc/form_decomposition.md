# Form Decomposition Tracking

## Objective

Every `@Form` annotation should contain **3–10 fields**. Forms with more than 10 fields
need decomposition into sub-sections to improve readability, maintainability, and usability.

## Approach

### Target Field Count

- **3–5 fields**: Ideal form size
- **6–10 fields**: Acceptable, no action needed
- **11+ fields**: Must be decomposed

### Decomposition Strategy by Size

**11–15 fields — Light split:**
- Add a `TextSection` for free-form narrative covering the full scope
- Split the `@Form` into 3–4 sub-classes (one per existing comment group)
- Parent keeps one field per sub-class + the TextSection

**16–35 fields — Standard decomposition:**
- Each `// --- Group Name ---` comment block becomes its own class with `@Form`
- Parent class shrinks to one field per sub-class
- Author can fill in a high-level description at the parent or drill into sub-sections

**36+ fields — Deep decomposition:**
- Same as standard, but sub-classes themselves may still be too large
- Apply splitting recursively — sub-classes get their own sub-classes
- Very large forms (100+) may need 2+ levels of hierarchy

### Mechanics

- Existing `// --- Comment Group ---` markers identify natural boundaries
- Each extracted group becomes a new class with `@Form`, `@SectionId`, and `@ContentHelp`
- Parent `@Form` is reduced to field references to these sub-classes
- Optionally add a `TextSection` at the parent for narrative overview
